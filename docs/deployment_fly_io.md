# Deploying to Fly.io (Conceptual Guide)

This document outlines the conceptual steps for deploying the Tenant Identity Lifecycle Lab application to Fly.io, based on the project issue description (Phase 9.2).

## 1. Prerequisites

-   A Fly.io account: Sign up at [fly.io](https://fly.io/).
-   The Fly.io command-line interface (`flyctl`) installed locally.
-   The application Dockerized (a `Dockerfile` exists at the project root).

## 2. Install Fly CLI (`flyctl`)

If you haven't already, install `flyctl`.

-   **macOS/Linux**:
    ```bash
    curl -L https://fly.io/install.sh | sh
    ```
    Follow the instructions to add `flyctl` to your PATH.
-   **Windows**: Instructions available on the Fly.io documentation (often via Scoop or PowerShell).

After installation, verify it:
```bash
fly version
```

## 3. Authenticate with Fly.io

Log in to your Fly.io account through the CLI:
```bash
fly auth login
```
This will typically open a browser window for you to authenticate.

## 4. Launch the Application on Fly.io (Initial Setup)

The `fly launch` command initializes your application on Fly.io. It inspects your project (looking for a `Dockerfile`) and generates a `fly.toml` configuration file.

Navigate to your project's root directory and run:
```bash
fly launch
```

You will be prompted for several pieces of information:
-   **App name**: Choose a unique name for your application (e.g., `tenant-id-lab`, `yourname-tenant-lab`). If left blank, Fly.io will generate one.
-   **Region**: Select a region where you want your app to be deployed (e.g., `iad` for Ashburn, US East; `ams` for Amsterdam, EU). Choose one close to you or your users.
-   **Organization**: Select the Fly.io organization to deploy under (usually your personal organization).
-   **PostgreSQL Database**: It might ask if you want to set up a Postgres database.
    -   For this project, we will manage this separately with `fly postgres create` (see next steps), so you can choose "No" or "Later" if prompted directly about DB setup during `fly launch` for the app itself. The `fly launch` for the app is primarily for the web service.
-   **Redis Cache**: Similarly, you can skip setting up Redis at this stage if prompted for the app.
-   **Deploy now?**: It's generally recommended to choose **"No"** or **"Later"** for the initial deployment. This allows you to review and customize the generated `fly.toml` file, set up secrets (like `DATABASE_URL`), and provision a database before the first deployment attempt.

After `fly launch` completes, a `fly.toml` file will be created in your project root. This file defines your application's configuration on Fly.io.

## 5. Review and Understand `fly.toml`

The `fly.toml` file is central to your Fly.io deployment. It specifies:
-   `app`: Your application's name.
-   `primary_region`: The main region for your app.
-   `build`: How to build your app (e.g., using the local Dockerfile).
-   `env`: Environment variables (non-secret).
-   `services`: Defines how your app serves traffic (ports, protocols, health checks).

A `fly.toml.example` file is provided in the project root with a common structure for a FastAPI application. You should compare this with the one generated by `fly launch` and adapt as needed. Key aspects for a FastAPI app include:
-   Correct internal port (e.g., `8000`, where Uvicorn runs).
-   HTTP health checks.

## 6. Provision PostgreSQL Database on Fly.io

Fly.io offers managed PostgreSQL clusters. You can create a free "starter" tier database suitable for this project.

1.  **Create a Postgres Cluster**:
    Run the following command. You'll be prompted to choose an app name for the database cluster (e.g., `tenant-id-lab-db`), a region, and potentially select a plan (choose a free/hobby tier if available).
    ```bash
    fly postgres create
    ```
    Follow the prompts. For example:
    -   App Name: `your-app-name-db` (e.g., `tenant-id-lab-db`)
    -   Region: Choose the same region as your application for low latency.
    -   VM Size/Plan: Select a small/free tier.

2.  **Attach the Database to Your Application**:
    Once the Postgres cluster is created, attach it to your main application (e.g., `tenant-id-lab`). This automatically sets the `DATABASE_URL` secret for your application, which it can use to connect to the database.
    ```bash
    fly postgres attach --app your-app-name your-app-name-db
    ```
    Replace `your-app-name` with your main application's name on Fly.io and `your-app-name-db` with the name you gave your Postgres cluster.

    You can verify the `DATABASE_URL` secret is set by running:
    ```bash
    fly secrets list -a your-app-name
    ```

## 7. Set Environment Variables and Secrets

Your application requires several environment variables to function correctly. Some are non-secret and can be in `fly.toml`'s `[env]` section. Secrets **must** be set using `fly secrets set`.

Key secrets to set:

-   **`SECRET_KEY`**: Your FastAPI application's secret key for JWTs, etc.
    ```bash
    fly secrets set SECRET_KEY="your_very_strong_random_secret_key_here" -a your-app-name
    ```
    *(Generate a strong key, e.g., using `openssl rand -hex 32`)*

-   **`IGA_API_URL`** (if IGA system is external and used by deployed app):
    ```bash
    fly secrets set IGA_API_URL="https://your-iga-system.example.com/api" -a your-app-name
    ```

-   **`IGA_API_KEY`** (if IGA system is external):
    ```bash
    fly secrets set IGA_API_KEY="your_iga_username:your_iga_password_or_token" -a your-app-name
    ```

-   **`PAM_API_URL`** (if PAM system is external):
    ```bash
    fly secrets set PAM_API_URL="https://your-pam-system.example.com/api" -a your-app-name
    ```

-   **`PAM_API_TOKEN`** (if PAM system is external):
    ```bash
    fly secrets set PAM_API_TOKEN="your_pam_api_token_here" -a your-app-name
    ```

**Important Considerations for IGA/PAM URLs:**
-   If your IGA and PAM systems are running locally for development, they won't be accessible by your Fly.io deployed application unless you expose them publicly (e.g., using ngrok, which is suitable for temporary demos but not production).
-   For a more permanent setup, your IGA/PAM systems would also need to be hosted with publicly accessible URLs, or within the same Fly.io organization and private network (more advanced setup).
-   If you are only using the conceptual IGA/PAM clients for now, you might not need to set these `IGA_*` and `PAM_*` secrets, or you can set them to dummy values. The application logic (e.g., in `IgaClient`, `PamClient`, and services) checks if these settings are present before attempting to make calls.

**Other Environment Variables**:
-   Variables like `POSTGRES_APP_USER`, `POSTGRES_APP_PASSWORD`, `POSTGRES_APP_DB` (used in `docker-compose.dev.yml`) are typically for local Docker Compose database setup. For Fly.io, the `DATABASE_URL` provided by `fly postgres attach` contains all necessary connection info for the managed database. Your application (and Alembic running via `Dockerfile` CMD or `release_command`) should be configured to use `DATABASE_URL`.
-   The `alembic.ini` file's `sqlalchemy.url` should ideally also be configured to read from the `DATABASE_URL` environment variable if it's to be used by a `release_command` in `fly.toml`. If migrations run from the Docker `CMD` (as currently configured), `env.py` (which uses `core.config.settings`) will pick up `DATABASE_URL` from the environment set by Fly.io.

After setting secrets, you might need to redeploy your application for them to take full effect, though new releases usually pick them up.

## 8. Deploying the Application to Fly.io

Once your `fly.toml` is configured, a PostgreSQL database is provisioned and attached (setting `DATABASE_URL`), and all necessary secrets are set, you can deploy your application.

1.  **Ensure Local Changes are Committed**:
    It's good practice to commit all your local changes to Git before deploying.

2.  **Run the Deploy Command**:
    From your project's root directory, execute:
    ```bash
    fly deploy
    ```
    -   `flyctl` will look at your `fly.toml` file.
    -   If your `fly.toml` specifies building from a local Dockerfile (as our example does), `flyctl` will start a remote Docker builder instance, send your project's context (files not ignored by `.dockerignore`) to it, build the Docker image, and then deploy the image to your Fly app's Machines.
    -   If you have a `release_command` in `fly.toml` (e.g., for database migrations: `alembic upgrade head`), it will run before the new version is released. If migrations are part of your Dockerfile's `CMD` (as in our current setup), they run when new Machines start.
    -   Monitor the output for any build or deployment errors.

3.  **Verify Deployment**:
    -   After `fly deploy` completes, it will usually show the URL of your application (e.g., `https://your-app-name.fly.dev`).
    -   Open this URL in your browser and test the application, including the UI (`/ui/`) and API endpoints.
    -   Check logs if you encounter issues: `fly logs -a your-app-name`.

## 9. CI/CD with GitHub Actions (Conceptual Outline)

Automating deployments using GitHub Actions can streamline the development workflow. When code is pushed to a specific branch (e.g., `main`), a GitHub Actions workflow can build and deploy your application to Fly.io.

### a. Create GitHub Actions Workflow File

-   Create a directory structure: `.github/workflows/` in your project root.
-   Inside, create a YAML file, e.g., `deploy.yml` or `fly_deploy.yml`.
-   A placeholder example (`.github/workflows/deploy.yml.example`) is provided in the project root, based on the issue description (Phase 9.3).

### b. Workflow Content (`deploy.yml.example` content)

The workflow would typically include steps like:
```yaml
name: Fly Deploy

on:
  push:
    branches:
      - main # Or your deployment branch

jobs:
  deploy:
    name: Deploy app
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v3

      - name: Set up Python (Optional - if running tests/linters in CI)
        uses: actions/setup-python@v4
        with:
          python-version: '3.10' # Match your app's Python version

      - name: Install dependencies (Optional - for tests/linters)
        run: |
          python -m pip install --upgrade pip
          pip install -r requirements.txt

      - name: Lint and Test (Optional - Placeholder)
        run: |
          # echo "Running linters..."
          # flake8 . --count --select=E9,F63,F7,F82 --show-source --statistics
          # echo "Running tests..."
          # pytest --maxfail=1 --disable-warnings -q
          echo "Skipping lint and test for now."

      - name: Deploy to Fly.io
        uses: superfly/flyctl-actions@1.3 # Check for latest version
        with:
          args: "deploy --config fly.toml --remote-only" # --remote-only uses remote builder
        env:
          FLY_API_TOKEN: ${{ secrets.FLY_API_TOKEN }}
          # You might need to pass other secrets as env vars if your fly.toml or Dockerfile needs them at build time
          # For runtime secrets, `fly secrets set` is preferred.
```

### c. Store `FLY_API_TOKEN` in GitHub Secrets

1.  **Generate a Fly API Token**:
    On your local machine, run:
    ```bash
    fly auth token
    ```
    Copy the displayed token. This token grants access to your Fly.io account.

2.  **Add to GitHub Secrets**:
    -   In your GitHub repository, go to "Settings" > "Secrets and variables" > "Actions".
    -   Click "New repository secret".
    -   Name the secret `FLY_API_TOKEN`.
    -   Paste the token value you copied.
    -   Click "Add secret".

### d. Workflow Explanation

-   **`on: push: branches: [main]`**: Triggers the workflow on pushes to the `main` branch.
-   **`jobs: deploy: runs-on: ubuntu-latest`**: Defines a job named `deploy` running on an Ubuntu environment.
-   **`actions/checkout@v3`**: Checks out your repository code.
-   **Setup Python, Install Dependencies, Lint/Test**: These are optional steps if you want to run checks in CI before deploying. The example skips them for brevity.
-   **`superfly/flyctl-actions@1.3`**: This GitHub Action sets up `flyctl` and runs the deploy command.
    -   `args: "deploy --config fly.toml --remote-only"`: Tells `flyctl` to deploy using your `fly.toml`. `--remote-only` is often recommended for CI to use Fly.io's remote builders.
    -   `FLY_API_TOKEN: ${{ secrets.FLY_API_TOKEN }}`: Securely provides the API token to `flyctl`.

### e. Pushing and Monitoring

-   Commit the `deploy.yml` (or `fly_deploy.yml`) file to your `.github/workflows/` directory.
-   Push your changes to the `main` branch (or your designated deployment branch).
-   Go to the "Actions" tab in your GitHub repository to monitor the workflow's progress.

This provides a basic CI/CD pipeline. You can expand it with more sophisticated testing, multi-environment deployments, etc.
